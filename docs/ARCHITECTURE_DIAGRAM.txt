╔════════════════════════════════════════════════════════════════════════════════╗
║                           ANTI-FARMING SAFEGUARDS                              ║
╚════════════════════════════════════════════════════════════════════════════════╝

Threat: Duplicate button tap
  → Solution: Unique event_key + unique(event_id, reward_key) in ledger
  → Result: First tap awards XP, retries return original result

Threat: Spam small workouts
  → Solution: cap_scope: "per_session", cap_count: 1
  → Result: One completion reward per workout session, no farming

Threat: Edit completed record to get more XP
  → Solution: Idempotency check on event_key
  → Result: Edits don't re-trigger rewards

Threat: Log protein 10 times in one day for +400 XP
  → Solution: cap_scope: "per_24h", unique(user_id, local_date)
  → Result: Only one +40 Muscle XP per 24-hour cycle

Threat: Submit fake PR achievement
  → Solution: PR requires like-for-like comparison with prior records
  → Result: Fake PRS detected and no bonus awarded

Threat: Client claims 1000 XP for self
  → Solution: Server calculates all XP from rules, never trusts client
  → Result: Client can only request; backend decides

Threat: Delete ledger entry to hide bad correction
  → Solution: Append-only ledger with foreign key constraints
  → Result: No deletion allowed; audit trail preserved


╔════════════════════════════════════════════════════════════════════════════════╗
║                         KEY SYSTEM PRINCIPLES                                  ║
╚════════════════════════════════════════════════════════════════════════════════╝

✓ SERVER IS AUTHORITATIVE
  • XP calculated server-side only
  • Levels derived from ledger
  • Ranks determined by backend
  • Client is display layer only

✓ LEDGER IS IMMUTABLE
  • No deletions
  • No edits
  • All corrections create new audit entries
  • Full history preserved

✓ EVENTS ARE IDEMPOTENT
  • Same event_key = same result always
  • Duplicate requests return original result
  • No double-awards for retries

✓ NON-PUNITIVE PROGRESSION
  • Missed days never subtract XP
  • Broken streaks never erase levels
  • Badges never removed
  • Users climb, never fall back

✓ VECTOR STABILITY REQUIRED
  • Rank promotions need minimum in EACH vector
  • Prevents one vector dominating
  • Harmony score monitors and gates progression

✓ DOMAIN OWNERSHIP
  • Habits own protocol definitions
  • Workouts own exercise records
  • Nutrition owns food logs
  • Each domain validates its own source records
  • XP ledger is centralized and shared

✓ CONFIGURATION OVER CODE
  • XP reward rules in JSON
  • Level thresholds in JSON
  • Rank requirements in JSON
  • Badge definitions in JSON
  • Easy to adjust without redeploying
